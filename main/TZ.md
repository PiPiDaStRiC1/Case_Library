# Назначение и цели создания системы

## Проблема

В библиотеке поиск изданий, проверка наличия, бронирование, выдача и возврат часто выполняются через разные каналы. Читатель не всегда понимает актуальный статус книги, а библиотекарь повторно вводит данные и ведёт параллельные журналы.

## Целевая аудитория

Основные пользователи: читатель и библиотекарь. Дополнительные пользователи: администратор библиотеки, руководитель сети и ИТ-администратор.

## Назначение системы

LibraFlow предназначен для централизованного каталога фонда, самообслуживания читателя и автоматизации ежедневных операций библиотеки.

## Цель создания системы

Разработать MVP, позволяющий найти книгу, проверить доступность, забронировать экземпляр, оформить выдачу, выполнить возврат и продлить срок пользования с фиксацией всех изменений.

## Задачи проекта

- разработать адаптивный Web-интерфейс читателя и сотрудника;
- реализовать backend на Node.js и REST API;
- спроектировать реляционную модель книг, экземпляров, пользователей и операций;
- реализовать поиск, фильтрацию, бронь и продление;
- реализовать выдачу, возврат, журналирование и права доступа;
- добавить импорт фонда из CSV;
- подключить email-провайдера для уведомлений;
- предусмотреть необязательное подключение API карт для филиалов;
- подготовить тестовые данные и документацию.

## Границы MVP

В MVP входят каталог, поиск, карточка издания, статусы экземпляров, личный кабинет, бронь, продление, рабочее место библиотекаря, выдача, возврат, роли, импорт CSV, email-уведомления и базовые отчёты.

## Что не входит в MVP

Не входят нативные мобильные приложения, RFID-оборудование, продажа книг, защищённое хранение цифровых копий, межбиблиотечный абонемент и ML-рекомендации.

# Предметная область

## Описание

Библиотечный фонд состоит из библиографических записей и физических экземпляров. Читатель взаимодействует с каталогом и создаёт бронь, библиотекарь подтверждает выдачу и возврат, а администратор управляет фондом и правилами.

## Текущий способ работы

Читатель ищет книгу на сайте или звонит в библиотеку. Сотрудник проверяет таблицу или локальную систему, вручную сообщает наличие и фиксирует операцию. Такой процесс не гарантирует единый актуальный статус.

## Ограничения предметной области

- один экземпляр не может быть одновременно выдан и забронирован другим читателем;
- продление невозможно при активной очереди;
- выдача доступна только авторизованному библиотекарю;
- смена статуса должна записываться в аудит;
- при сбое внешнего сервиса критическая операция не должна теряться.

# Основной бизнес-процесс

## Наименование

Поиск, бронирование, выдача и возврат библиотечного экземпляра.

## Участники

Читатель, библиотекарь, администратор, LibraFlow, email-провайдер и при необходимости API карт.

## Шаги процесса

1. Читатель ищет издание и выбирает филиал.
2. Система показывает доступность экземпляров.
3. Читатель создаёт бронь.
4. Система фиксирует бронь и отправляет уведомление.
5. Библиотекарь подтверждает выдачу.
6. Система устанавливает срок возврата.
7. Библиотекарь регистрирует возврат.
8. Система освобождает экземпляр или активирует следующую бронь.

# Функциональные требования

## Общие положения

Система состоит из frontend-приложения, backend-приложения и базы данных. Взаимодействие выполняется через REST API. Внешние сервисы используются через отдельные адаптеры и не являются единственным хранилищем критических операций.

## Аутентификация и авторизация

- система должна поддерживать вход пользователя;
- API должен проверять роль и право операции;
- читатель не должен видеть данные другого читателя;
- операции сотрудника должны попадать в журнал аудита.

## Каталог и поиск

- система должна хранить название, авторов, ISBN, тему и описание;
- пользователь должен искать по названию, автору, ISBN и теме;
- должны быть фильтры по филиалу и доступности;
- карточка должна показывать время последнего обновления.

## Бронь и продление

- читатель должен создать бронь доступного экземпляра;
- система должна назначить срок хранения брони;
- система должна запретить конфликтующие брони;
- продление должно проверять очередь и лимит продлений;
- читатель должен получить понятную причину отказа.

## Выдача и возврат

- библиотекарь должен найти читателя и его активные брони;
- выдача должна проверять ограничения;
- возврат должен изменить статус экземпляра;
- при наличии очереди система должна предложить следующего читателя;
- каждая операция должна фиксировать время, пользователя и результат.

## Импорт и внешние API

- администратор должен загрузить фонд из CSV;
- система должна показать ошибки строк до публикации импорта;
- email-провайдер должен использоваться для подтверждений и напоминаний;
- API карт может использоваться для отображения филиалов и координат;
- при недоступности API карт каталог и операции должны продолжать работу.

# Требования к данным

Основные сущности: `User`, `Role`, `Book`, `Author`, `BookAuthor`, `Copy`, `Branch`, `Reservation`, `Loan`, `Notification`, `AuditLog`.

Для сущностей должны соблюдаться уникальность ISBN и идентификатора экземпляра, ссылочная целостность авторов и книг, допустимые переходы статусов и обязательность дат создания и изменения.

---

# Нефункциональные требования

## Производительность

- поиск по каталогу до двух секунд при тестовом фонде не менее ста тысяч записей;
- операция бронирования должна отвечать до трёх секунд;
- повторная отправка запроса не должна создавать дублирующую бронь.

## Надёжность

- ошибки API должны возвращать понятный HTTP-статус и сообщение;
- изменения статуса должны выполняться атомарно;
- сбой email или карт не должен отменять уже сохранённую операцию;
- импорт должен быть повторяемым и иметь журнал ошибок.

## Безопасность

- пароли не хранятся в открытом виде;
- доступ к операциям ограничивается ролью;
- персональные данные выдаются только уполномоченному пользователю;
- внешние ключи и токены хранятся в переменных окружения;
- действия сотрудников журналируются.

## Удобство использования

Интерфейс должен быть адаптивным, иметь понятные статусы и сообщения об ошибках, поддерживать клавиатурную навигацию на основных формах и сохранять рабочий сценарий при временной недоступности необязательного API карт.

# Критерии приёмки MVP

- читатель находит книгу по названию и видит доступность;
- читатель создаёт бронь и получает подтверждение;
- библиотекарь оформляет выдачу и возврат;
- продление блокируется при наличии очереди;
- импорт CSV показывает ошибки и не публикует некорректные строки;
- статусы экземпляров не противоречат друг другу;
- права ролей проверяются на backend;
- внешние API не блокируют каталог и основные операции;
- интерфейс корректно работает на ноутбуке и мобильном экране;
- все изменения статусов доступны в журнале аудита.

# Ограничения и допущения проекта

Проект рассчитан на пилот одной библиотеки или небольшой сети. Фонд импортируется из CSV, а правила выдачи задаются администратором. API карт считается необязательной интеграцией. Средний чек, объём рынка и нагрузочные показатели из аналитических артефактов являются учебными оценками.
